# AutoApply Constitution

AutoApply finds tech jobs that match the user's preferences, tailors the user's resume per job and
applies (or fills forms) on their behalf, running unattended overnight with a local LLM. Single user,
self-hosted, Brazil-only jobs for now.

## Core Principles

### I. Zero Fabrication (NON-NEGOTIABLE)
Every claim the system writes (tailored resume, cover letter, form answer) MUST be backed by at least
one `Fact` sourced from the user's base resume, LinkedIn profile, GitHub or user-entered data.
- LLM output schemas MUST carry `evidence: factId[]`; empty evidence = invalid output.
- A deterministic validator (no LLM) MUST check every technology, company, title and number in the
  output against the cited facts. Failure → one retry → `needs_input`.
- Numbers (years of experience, counts, percentages) are computed by code or copied verbatim from a
  fact, never generated by the LLM.
- When there is no evidence for a yes/no or skill question, the answer is the lowest honest option
  or `needs_input`. Never "yes".
- Unverified facts (`verifiedByUser=false`) are never used outside dry-run.

### II. Human in the Loop by Default
Modes: `dry-run` (fill, screenshot, never submit) → `review` (default: user approves in batch) →
`autopilot` (opt-in, only when score and every answer confidence clear thresholds AND `make eval`
reports 0 fabrications). Any unknown question, captcha, expired session or validation failure parks
the application in `needs_input`. The UI always has a working kill switch.

### III. Respect Platforms
Daily caps per source, concurrency 1 per logged-in platform, backoff on errors. No captcha solving,
no fingerprint spoofing or anti-bot evasion built by us. Prefer official/public APIs (Greenhouse,
Lever, Ashby, Gupy portal API) over scraping. LinkedIn is opt-in with a low cap because its terms
forbid automation.

### IV. Local-First AI
Default LLM runs on Ollama on the host (16GB RAM: `qwen3:8b` text, `bge-m3` embeddings,
`qwen2.5vl:7b` vision fallback). All LLM calls go through the `LlmProvider` interface in
`packages/llm`; a cloud provider is an optional, explicit fallback. Every LLM output is validated
with Zod.

### V. Typed Contracts, Simple Services
TypeScript strict everywhere, shared Zod schemas in `packages/shared`. Services talk through BullMQ
queues whose names and payload schemas live in `packages/shared`. Python only where the ecosystem
requires it (`services/scraper`, JobSpy). No new service, queue or dependency without a spec that
justifies it. YAGNI.

### VI. Testable and Observable
Each adapter (job source / apply platform) has fixture-based tests (saved HTML/JSON). Every pipeline
step emits a `RunEvent`; every submit stores before/after screenshots in MinIO. Test failures are
reported, never hidden.

## Technology Constraints

Next.js (App Router) + TailwindCSS + shadcn/ui · NestJS · PostgreSQL 16 + pgvector · Prisma · Redis +
BullMQ · MinIO (S3 API) · Playwright · Ollama · Docker Compose · Makefile · pnpm workspaces +
Turborepo · Python 3.12 + uv for `services/scraper`. Secrets only in `.env` (never committed);
platform sessions stored encrypted (`SESSION_ENCRYPTION_KEY`).

## Development Workflow

Spec-Driven Development with Spec Kit: `/speckit-specify` → (`/speckit-clarify`) → `/speckit-plan`
→ `/speckit-tasks` → (`/speckit-analyze`) → `/speckit-implement`. One feature branch + one
`specs/NNN-name/` folder per roadmap item in `docs/roadmap.md`. Keep `CLAUDE.md` and
`docs/architecture.md` updated when a feature changes architecture. Refresh the code graph with
`make graph` after structural changes.

## Governance

This constitution overrides other practices. Amendments require editing this file with a version
bump and a note in the commit message. Plans that violate a principle must justify it in the plan's
Complexity Tracking section.
