# Research: Logged-in Platforms and Assisted Real Submission (F5)

Decision / Rationale / Alternatives.

## R1. Platform model replaces per-ATS caps

- **Decision**: new table `Platform` keyed by `kind` (`gupy | linkedin | greenhouse | lever | ashby |
  generic`), seeded on first use with defaults: caps (submissions/simulations per day), safe maximums,
  minimum interval, pause/backoff state, LinkedIn opt-in, and — for `gupy`/`linkedin` — the encrypted
  session. `SearchPreference.applyDailyCap` (F4) is removed; `applyConfidence` stays. `Source`
  (discovery) is untouched: its `sessionEnc` stays unused (discovery uses the LinkedIn MCP session).
- **Rationale**: one place for "what may run on this platform today", shared by simulations and
  submissions; discovery sources and apply platforms are different concepts (LinkedIn MCP ≠ Easy Apply).
- **Alternatives**: reuse `Source` (mixes discovery and apply; no rows for Greenhouse/Lever/Ashby).

| kind | submit cap | simulate cap | max (submit) | min interval |
|---|---|---|---|---|
| gupy | 15 | 30 | 40 | 60 s |
| linkedin | 5 | 10 | 15 | 180 s |
| greenhouse / lever / ashby / generic | 20 | 30 | 50 | 30 s |

## R2. Session connect: manual login in a visible window (FR-001..FR-004)

- **Decision**: API `POST /platforms/:kind/connect` enqueues `connect-session` on the existing `apply`
  queue. The worker launches a **headed** Chromium (`headless: false`) on the user's desktop, opens the
  platform login page (`https://login.gupy.io/candidates/signin`, `https://www.linkedin.com/login`),
  and polls every 2 s until one of: logged-in signal (LinkedIn: `li_at` cookie; Gupy: leaving the
  login host with an auth cookie on `*.gupy.io`), the user clicks "Concluí" in the UI
  (`POST /platforms/:kind/connect/done` sets `Platform.connectRequest = 'done'`), the window is closed
  (cancel), or 10 min timeout. Then `context.storageState()` → encrypted → `Platform.sessionEnc`.
  The system never touches the login form (no fill/click in that window). Account label: page title /
  profile name when visible, else null.
- **Encryption**: AES-256-GCM, key = `SESSION_ENCRYPTION_KEY` (64 hex chars, generated by `make setup`),
  random 12-byte IV, stored as `v1:<iv>:<tag>:<ciphertext>` base64. Missing/invalid key or failed auth
  tag → session unusable → status `expired` ("reconectar"); never a plaintext fallback.
- **Test session**: `test-session` job opens a headless context with the session on a logged-in page
  (Gupy `https://www.gupy.io/candidates/applications`? → generic: `https://login.gupy.io` redirect
  check; LinkedIn `https://www.linkedin.com/feed/`) and classifies valid / expired (login wall or
  two-factor prompt) through the dry-run guard (read-only).
- **LinkedIn opt-in**: `Platform.optInAt` must be set (`POST /platforms/linkedin/opt-in` with explicit
  confirmation text) before connect; the existing `make linkedin-login` (MCP container) is unrelated
  and kept.
- **Alternatives**: store credentials and log in automatically (forbidden by FR-002); reuse the MCP
  container profile (different browser, not Playwright storageState).

## R3. Preparing on logged-in platforms = F4 engine + session + two adapters (FR-005, FR-006)

- **Decision**: `openDryRunContext(browser, { storageState })` (same guard; session cookies only make
  pages render as logged in). `detectAts` gains `gupy` (`*.gupy.io` job/apply URLs) and `linkedin`
  (`linkedin.com/jobs/view/<id>`, `currentJobId=`). New adapters:
  - **gupy**: job page → "Candidatar-se" click is a navigation (GET) to the application flow; extract
    per step with the F4 extractor; Gupy-specific signals: already applied ("Você já se candidatou",
    "Candidatura enviada"), login redirect (expired), "teste online/vídeo" steps (follow-up note).
  - **linkedin**: job page → Easy Apply button (`.jobs-apply-button` with "Candidatura simplificada" /
    "Easy Apply") opens the modal `[data-test-modal-id="easy-apply-modal"], .jobs-easy-apply-modal`;
    steps advance with "Avançar/Next/Revisar/Review" (submit = "Enviar candidatura/Submit
    application", never clicked in preparation); "follow company" checkbox is unchecked; resume step
    picks the uploaded file input when present. No Easy Apply → follow the external apply link and run
    the F4 engine on it.
- **Known limit (documented, not hidden)**: steps that only advance after the platform saves the step
  (POST blocked by the dry-run guard) cannot be prepared; preparation then covers the reachable steps
  and the submit run (R5) verifies each later step — unknown required fields there stop the submission
  with `new_step` listing them, the user answers, re-approves, and the run starts over.
- **Unusual activity / rate limit**: `detectBlockers` gains `unusual_activity` (LinkedIn "atividade
  incomum", "unusual activity", HTTP 429/999, Gupy "muitas tentativas") → platform paused (R6).
- **Fixtures**: no account may be created or used by the agent, so the first fixtures are synthetic
  HTML reproducing the public structure of the Gupy flow and the LinkedIn modal (labels, button texts,
  step navigation in page script). `snapshot-form.ts --session <kind>` lets the user re-record real
  logged-in pages (snapshots stay local, gitignored under `data/fixtures/` until reviewed for PII).

## R4. Approval (FR-007, FR-014)

- **Decision**: `POST /applications/:id/approve` (and batch `POST /applications/approve { ids }`)
  requires `status = ready`, mode `review` (`SearchPreference.mode`; `dry_run` → 409 `dry_run_mode`),
  not outdated (F4 rule), platform connected when it needs a session. It stores `approvedAt` and
  `approvalHash = sha256(formUrl, sorted (fieldKey, answer), tailoredDocIds+updatedAt)` and moves the
  application to `approved`, enqueuing `submit` on queue `apply`. Any re-simulation clears approval.
- **Rationale**: the hash ties the approval to exactly what the user saw.

## R5. Submit path (FR-007..FR-011, FR-013)

- **Decision**: `apps/worker/src/apply/submit.ts` — the only code allowed to submit. It opens
  `openSubmitContext(browser, { storageState })`: a context without the dry-run network guard or submit
  trap (it must be able to submit), still with `serviceWorkers: 'block'`. Flow:
  1. Checks: application `approved`, `approvalHash` recomputed from DB equals stored, platform not
     paused, caps/interval OK (else delayed), kill switch.
  2. Open form via the adapter, per step: extract fields → **verify** against stored `FormAnswer`s of
     that step: same keys, same options, no new required field without an approved answer → else stop
     with `form_changed` / `new_step`. Fill exactly the stored values (no LLM, no new answers), attach
     the PDF re-rendered from the same tailored document (its `updatedAt` must match), screenshot.
  3. Final step: **compare-and-set** `UPDATE Application SET status='submitting' WHERE id=? AND
     status='approved'` — if 0 rows (kill switch / concurrent run) abort without clicking. Then click
     the adapter's submit control once.
  4. Outcome (≤ 30 s): confirmation detected (adapter patterns: "Candidatura enviada", "Application
     submitted", "Thank you for applying", Easy Apply "Sua candidatura foi enviada", URL `/confirmation`)
     → `submitted` + `confirmation` screenshot + `sentValues`; captcha/human check appears → assisted
     submit (R5b); nothing detected / error after click → `submit_uncertain` (never retried; the user
     marks it sent / not sent in the UI).
  - BullMQ job for `submit` has `attempts: 1`; a run that finds `submitting|submitted|submit_uncertain`
    exits immediately (idempotency, FR-009).
- **R5b Assisted submit**: same steps 1–2 in a **headed** browser; inject a fixed banner ("Conclua a
  verificação e clique em enviar — AutoApply não envia nem resolve captcha"); set `submitting_assisted`;
  wait up to 15 min for a confirmation pattern (submitted, `via: assisted`), or window closed /
  timeout → back to `needs_input` (`human_check`), approval kept. The system never clicks inside the
  captcha nor the submit button in this mode.
- **Alternatives**: submit inside the dry-run engine with a flag (rejected: one bug would submit in
  dry-run; F4 guarantee must stay structural).

## R6. Caps, interval, pause (FR-012, FR-015)

- **Decision**: before any simulation or submission the processor calls `platformGate(kind, action)`:
  paused (`pausedUntil > now` or `paused = manual`) → delay until then; today's count (simulations:
  `Application.lastRunAt` per platform; submissions: `submittedAt` + `submitting`) ≥ cap → delay to
  00:05 tomorrow (`daily_cap`); `now - lastActionAt < minInterval` → delay the remainder. It then sets
  `lastActionAt`. Concurrency 1 is global (the `apply` worker has concurrency 1). Errors: 2 consecutive
  platform errors → backoff level +1 (1 h, 4 h, manual); `unusual_activity` → manual pause. Caps above
  the maximum → 422.

## R7. Kill switch (FR-013)

- **Decision**: `POST /apply/stop` additionally removes waiting/delayed `submit` jobs and sets
  `approved` applications back to `ready` (approval cleared, reason `cancelled`). A running submission
  aborts at the compare-and-set (R5.3) and between steps.

## R8. Tests (FR-016)

- **Decision**: crypto round-trip + tamper tests; adapter tests on synthetic Gupy/LinkedIn fixtures
  (dry-run); submit-path tests against a local test form served via `serve` that **records** POSTs —
  approved run submits exactly once with the approved values; changed form → `form_changed`; kill
  switch at compare-and-set → not submitted; no confirmation → `submit_uncertain`; second run → no-op;
  assisted flow with a fake "human" (test clicks submit in the headed-equivalent context). Connect flow
  tested with a fake login page that sets a cookie. Never against a real platform.
